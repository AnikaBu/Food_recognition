# Правила разработки проекта Food Recognition

## 1. Правило фиксации этапов (Git Push Rule)
- После каждого логически завершенного этапа и обязательной проверки работоспособности:
  1. Обновить статус в `ROADMAP.md` (отметить выполненные пункты галочками).
  2. Создать понятный коммит в Git (например: `feat: add SQLite nutrition diary module (stage 2)`).
  3. Выполнить отправку в удаленный репозиторий (`git push origin main`).
- Предлагать пользователю переход к следующему этапу только после подтверждения текущего.

## 2. Безопасность и приватность
- Ни при каких условиях не коммитить файл `.env`, API-ключи, токены или пароли.
- Не коммитить пользовательские базы данных (`*.db`) и личные фотографии еды.
- Все временные файлы и медиа должны отсекаться файлом `.gitignore`.
- Обработка изображений блюд производится исключительно в оперативной памяти (`io.BytesIO`) без сохранения файлов на диск.
- **Защита от утечек (Gitleaks Pre-commit Hook)**: в репозитории настроен pre-commit hook (`.githooks/pre-commit`, активируемый через `git config core.hooksPath .githooks`), проверяющий индексированные (`staged`) файлы на наличие паролей, API-ключей и токенов с помощью `gitleaks`. При обнаружении секретов коммит блокируется.

## 3. Архитектура
- Принцип: «Один бэкенд (Python / FastAPI) — три клиента (Telegram-бот, PWA, Android/Flutter)».
- Логика распознавания и база данных сосредоточены в бэкенде, чтобы клиенты не дублировали код.

## 4. Технические особенности и опыт (Lessons Learned)
- **Модели Gemini Vision**: актуальными являются `gemini-3.5-flash-lite` и `gemini-3.8-flash`. Старые версии (`1.5-flash`, `2.5-flash`) недоступны для новых аккаунтов. При временных пиках нагрузки (503) используется повторная попытка с задержкой 1.5 сек.
- **GitHub токены**: для пуша в персональные репозитории используется универсальный Classic PAT (`ghp_...`) с областью `repo`.
- **Валидация изображений в FastAPI**: не следует полагаться исключительно на заголовок `file.content_type`, так как мобильные клиенты (например, Flutter `http.MultipartFile.fromBytes`) по умолчанию выставляют `application/octet-stream`. Проверку формата надежнее выполнять анализом байт через Pillow (`Image.open(bytes).load()`).
- **Брендинг MyFoodDiary**: проект стандартизирован под именем `MyFoodDiary` на всех клиентах (ярлык `android:label`, PWA манифест, заголовки API и Telegram-бот).
- **E2E UI-тестирование (Playwright)**: для автоматической проверки кнопок и сценариев веб-интерфейса используется Playwright (`test_frontend.py`). Элементы внутри модальных окон/карточек должны быть предварительно видимы (не `display: none`), а браузерные диалоги `window.confirm()` обрабатываются через регистратор события `page.once("dialog", lambda d: d.accept())`.
- **Персистентность настроек и целей КБЖУ**: цели пользователя (калории, белки, жиры, углеводы) хранятся в таблице `nutrition_goals` SQLite и синхронизируются через `GET/PUT /api/goals`. Мобильные клиенты используют двустороннюю синхронизацию (загрузка с сервера + локальный кэш), предотвращая сброс данных при переустановке или обновлении приложения.
- **Система In-App автообновления для Flutter**: проверка новых версий выполняется через GitHub Releases API (`/releases/latest`), версия сравнивается по SemVer. Для обновления APK внутри приложения в `AndroidManifest.xml` добавляются разрешение `android.permission.REQUEST_INSTALL_PACKAGES` и секция `<queries>` для открывающих интентов.
- **Сборка Flutter с AGP 9+ и автообновление без нативных конфликтов**: в современных версиях Android Gradle Plugin (AGP 8.9+/9+) устаревшие плагины скачивания (вроде `ota_update`) приводят к ошибкам DSL. Использование официального `url_launcher` для передачи APK системному загрузчику и флагов `android.newDsl=false`, `android.builtInKotlin=false` в `android/gradle.properties` обеспечивает стабильную сборку в CI/CD без конфликтов.
- **Запуск скачивания APK на Android 11+ через url_launcher**: прямой вызов `canLaunchUrl(apkUri)` для ссылок, оканчивающихся на `.apk`, часто возвращает `false` из-за особенностей сопоставления MIME-типов в Android `PackageManager`. Чтобы системный браузер или загрузчик успешно открывал прямую ссылку на APK, вызов `launchUrl(uri, mode: LaunchMode.externalApplication)` следует выполнять напрямую в блоке `try-catch` (с запасным `platformDefault`), а в `AndroidManifest.xml` добавлять `<uses-permission android:name="android.permission.QUERY_ALL_PACKAGES"/>`.
- **Реактивная синхронизация настроек и целей КБЖУ в Flutter**: при навигации через `IndexedStack` дочерние экраны сохраняют состояние и не вызывают `initState` повторно при переключении вкладок. Чтобы изменения целей КБЖУ мгновенно отражались на главном экране дневника без перезапуска приложения, `SettingsService` реализуется как `ChangeNotifier` с уведомлением подписчиков (`notifyListeners()`), `DiaryScreen` подписывается на него в `initState` (`addListener`) и отписывается в `dispose`, а на переключение вкладок и `RefreshIndicator` назначается принудительное обновление целей и сводки.
- **Постоянный ключ подписи (Keystore) в GitHub Actions CI/CD**: если при каждой сборке генерировать `release.jks` с помощью `keytool`, каждая новая версия APK получает уникальный случайный сертификат. Android отклоняет установку такого обновления поверх существующего с ошибкой `INSTALL_FAILED_UPDATE_INCOMPATIBLE` («Приложение не установлено, так как оно конфликтует с другим пакетом»). Для бесшовных In-App автообновлений в репозитории зафиксирован постоянный ключ подписи (в base64), который скрипт сборки разворачивает перед `flutter build apk`.
